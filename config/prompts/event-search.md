# Event Search (P-02)

## 任务

分析当前 Content，提取用于召回**历史 Event 信息主线**的临时检索线索。一篇 Content 可以涉及多个不同事项，需要分别提取。此阶段不做新旧 Event 归属判断、不评估事实增量、不确认并保存实体别名。

## 1. 识别持续事项

识别有事实依据的事件、状态变化或持续事项，例如：
- 核心实体发生的现实变化；
- 监管、技术、商业、科研、政策等事项的进展；
- 能围绕核心对象和主题持续追踪的事实。

纯观点、预测、假设情境或背景知识不作为已经发生的事件事实。同一实体、同一持续事项的多个细节应合并为一组线索；不同事项可以分组。

## 2. Entity 识别

`entity_name` 是事项的**核心实体**，例如公司、机构、人物、产品、项目或明确的政策对象。
- 选择最能代表信息主线身份的对象；不枚举文章提及的所有参与者。
- 某公司接受监管调查时，通常以被调查公司作为核心实体，监管机构为参与方。
- 不把不同实体、母子公司、公司与产品误当成同一个 Entity。

## 3. Subject 识别

`subject` 是围绕 Entity 持续发展的事项主题。使用稳定简洁的表达，如“反垄断监管”“大模型研发”“企业经营重组”。
避免将“昨天发布公告”“本周召开会议”等短期动作当作整个 Subject。

## 4. Search Terms 生成

为每组 Entity + Subject 提取少量有用的检索词，可以包括：
- 核心 Entity 正式名称、本文确实出现的简称/英文名/缩写；
- Entity 与 Subject 的组合词；
- 该事项的常见表达和合理同义说法。

优先基于 Content 中出现的事实与名称，可做克制的同义表达扩展；不要虚构具体名称、事件或历史事实。检索词应同时帮助命中实体索引和 FTS5 文本，避免大量宽泛无区分度的词。

跨语言 Content 不需要先翻译全文：
- `entity_name` 优先保留原文官方或规范名称，不强行翻译。
- `subject` 使用简洁中文表达，便于召回既有中文 Event；无法可靠概括时保留原文，不编造含义。
- `search_terms` 同时保留原文正式名称、简称、英文名、缩写，以及有明确依据的中文对应表达，帮助跨语言召回历史 Event。
- 无法确定中文名称或译名时只保留原文，不创造译名；中文检索词同样只是临时线索，不是已确认别名。

**所有 search_terms 都是临时检索线索，不是已确认别名，绝不能直接写入 `event_entity_aliases`。**

## 5. 多事项与边界

- 一篇文章可以输出多组 `clues`；同一事项的多个动作尽量合并。
- 同一实体可以对应多个不同 Subject，不因主体相同而合并不同事项。
- 不读取历史 Event 或 Update；无历史候选也不影响后续 P-03 决策。
- 不使用 User Context、Topic 或用户兴趣调整事实线索。
- 不判断 `NEW_EVENT` / `NEW_UPDATE` / `NO_INCREMENT`。
- `PARTIAL` Content 仅根据实际提供的文本提取，不补造事实。
- 无可识别事件事实时返回空 `clues`。

## 输出要求

严格按程序提供的 JSON Schema 返回：
- `clues[]`
- 每项 `entity_name`、`subject`、`search_terms[]`

不生成 Event ID，不返回确认别名、评分、理由或额外字段。
