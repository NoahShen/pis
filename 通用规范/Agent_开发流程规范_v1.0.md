# Agent 协作开发流程规范

> **版本**：v1.0  
> **日期**：2026-11-14  
> **定位**：跨项目通用基线（项目无关）  
> **状态**：初版，可作为项目定制规范的基础  
> **适用范围**：使用一个或多个 AI Agent 参与软件设计、开发、测试与交付的个人项目及小团队项目。

## 1. 目标与核心原则

本规范主要解决：Agent 长会话导致上下文膨胀、要求与设计在对话中漂移、反复修改而无法收敛、跨会话接续困难及缺少客观验收证据。

1. **文件是长期状态，对话是短期工作区**：已批准的文档、Git 提交和结构化进度记录是权威依据；聊天历史不是项目数据库。
2. **先约定再实施**：`intent.md → spec.md → plan.md` 逐级审核，门禁通过后才进入下一阶段。
3. **一个任务，一个主要目标**：每次仅向 Worker 交付一个可独立验证的任务，避免让单个会话承担整个项目。
4. **设计与实现分离**：实现须遵守已批准的业务目标和技术契约；遇到冲突时上升到对应设计层处理，不能靠连续补丁替代设计决策。
5. **以证据验收**：测试结果、代码差异、可复现缺陷和明确契约是审核依据；不以 Agent 自我评价代替验收。
6. **最低必要治理**：流程是为减少返工服务；不因流程引入无必要的 Agent、服务、数据库或重复文档。

## 2. 角色与职责

| 角色 | 主要职责 | 不应做的事 |
|---|---|---|
| **项目负责人（人）** | 确认目标、范围、关键取舍；批准 `intent.md` 及需要人工决定的重大设计变更 | 被迫审核每个普通代码细节 |
| **Architect** | 根据需求编写/审核技术规格，维护项目架构约束；审核里程碑计划；逐任务检查实现是否符合设计 | 在代码审核时无依据地重新发明需求或随意扩展范围 |
| **Lead** | 将已批准规格转成文件级任务计划；按依赖派发任务；审核 Worker 的代码、测试与变更范围；维护进度 | 将整项里程碑一次性交给 Worker 或代替负责人作重大产品决策 |
| **Worker** | 在授权范围内编码、自测、提交证据和交接记录 | 私自改需求、扩展接口、修改无关模块或宣布自己已最终验收通过 |

角色是**职责分离**，不强制对应不同模型或长期驻留的 Agent。资源有限时可由同一模型在**不同、重新初始化的会话**中承担多种职责；作者与审核者尽量隔离上下文。

**审核路径**：Worker 自测 → Lead 功能/代码审核 → Architect 设计一致性复核。每完成一个任务即进行 Architect 的**轻量复核**；仅对跨模块改动、契约变化及重大风险做更深审查，避免重复审查相同细节。

## 3. 文档体系与单一事实来源

### 3.1 推荐结构

```text
<repository>/
├── AGENTS.md                         # Agent 进入项目的简短导航，不复制完整规范
├── docs/
│   ├── architecture.md               # 项目级长期架构基线（若适用）
│   ├── project-development.md        # 本项目对通用规范的补充/显式覆盖
│   └── milestones/
│       └── <milestone-id>/
│           ├── intent.md             # 目标、边界和成功定义
│           ├── spec.md               # 可审核的技术契约
│           ├── plan.md               # 任务列表、依赖、文件级实现计划
│           └── progress.md           # 执行状态、证据、提交与阻塞
└── ...
```

此结构是默认建议，不强制已存在项目调整目录。项目级设计和测试基线继续作为权威来源；里程碑文档以**引用具体章节**的方式复用，不复制整套设计。

### 3.2 文档边界

| 文档 | 回答的问题 | 必填内容 | 避免写入 |
|---|---|---|---|
| `intent.md` | **为什么做、做到什么程度？** | 背景/问题、目标、范围、非目标、用户可观察结果、成功标准、关键约束及未决决策 | 实现细节、具体函数和文件列表 |
| `spec.md` | **系统怎样满足需求？** | 与既有架构的关系、关键数据/接口契约、处理流程、边界及错误行为、风险、可测试验收条件 | 文件级任务拆解、施工日志、重复的业务需求全文 |
| `plan.md` | **怎样以小任务落地？** | 有序任务 ID、依赖、允许修改的文件/模块、实现步骤、引用的 spec 条款与测试 Case、验证命令、验收出口 | 重定义上游需求或替代 spec 作出架构决策 |
| `progress.md` | **现在执行到哪里？** | 任务状态、结果、提交 ID、验证证据、阻塞、剩余工作 | 完整聊天记录、冗长终端日志、隐式设计变更 |

`progress.md` 是**执行记录**，不是第四层设计门禁。若某个项目已拥有批准的需求/技术规格/任务清单，应先做**映射和引用**，不得机械重写而形成竞争版本。

### 3.3 文档状态与优先关系

- 设计文档状态：`DRAFT → REVIEW → APPROVED → SUPERSEDED`。
- 审核结论必须留存：审核者、日期、结论、阻塞项；Git 提交（或版本标识）定位批准的基线。
- `intent` 不能违背项目级已确认的业务原则；`spec` 不能静默改变 `intent`；`plan` 不能静默改变 `spec`；代码不能静默改变 `plan` 的授权边界。
- 当发现冲突，停止受影响任务，明确冲突来源，在相应上游文档修订并审核受影响的下游内容。**已批准不等于永远不可修改；变更必须显式、可追溯。**

## 4. 三文档门禁

### G1：Intent Gate（目标审核）

**负责人**：Architect 起草，项目负责人批准。

检查：问题是否真实；目标和非目标是否清楚；成功能否被观察或验证；关键依赖/未决问题是否已标明；是否与项目长期目标冲突。

**通过条件**：所有阻塞性问题均已解决或明确划归到指定后续决策点；`intent.md` 标记 `APPROVED`。

### G2：Spec Gate（设计审核）

**负责人**：Architect；涉及重要业务/架构取舍时由项目负责人确认。

检查：是否满足 intent；接口、数据、不变量及错误分支是否清楚；是否符合既有架构；哪些行为是必须测试的；是否包含没有必要的抽象或新组件。

**通过条件**：无影响实现方向的未决设计冲突；规格可以成为客观验收依据；`spec.md` 标记 `APPROVED`。

### G3：Plan Gate（实施审核）

**负责人**：Lead 起草，Architect 审核。

检查：任务依赖是否正确；任务是否能独立验收；每张任务卡是否引用批准的规格和测试；文件修改边界是否明确；集成顺序和回滚/恢复是否可行。

**通过条件**：首个任务可由全新 Worker 会话执行；`plan.md` 标记 `APPROVED`。**未通过 G3 不开始正常开发**（明确标记的技术验证/原型除外，其结果不得直接代替正式验收）。

## 5. 从里程碑到小任务

1. **按可交付能力划里程碑**，不要用整个项目的一份巨型 `plan.md`；相互独立的业务模块宜拆开验收。
2. **按可验证增量划任务**：推荐一个主要职责、一个清晰输出、一组相关修改文件及定向测试。任务大小以“新会话能够理解、实现并自测”为准，既不把多个系统串成一个任务，也不拆成不能独立验证的琐碎操作。
3. **优先稳定契约与依赖**：基础设施、数据定义、公共接口可先实现；未完成的上下游用最小 Stub/Fake 隔离。
4. **先局部闭环，后全链路集成**：单任务通过不代表里程碑通过；里程碑还必须过组合/边界测试。
5. **控制并发**：同一文件或接口所有权不清时串行；确有并行价值时使用独立分支/worktree，并约定集成责任。

### 标准任务卡最小字段

```yaml
id: M01-T03
title: 实现某个可验证能力
status: READY
baseline: <已批准的 spec/plan 版本或 commit>
depends_on: [M01-T01]
spec_refs: ["spec.md#3.2"]
allowed_paths: ["src/feature/", "tests/feature/"]
required_context: ["相关接口定义", "相关测试用例"]
acceptance:
  - 必须满足的行为或不变量
verification:
  - npm run typecheck
  - npm test -- <target>
```

命令和文件名只是模板；实际值由项目定制，不把 Node.js 或特定测试工具作为通用要求。

## 6. 任务执行与会话生命周期

**任务状态**：`NOT_STARTED → READY → IN_PROGRESS → REVIEW → PASS`；审核未通过转 `FAIL` 并回到 `IN_PROGRESS` 修复；外部依赖或设计缺失时标记 `BLOCKED`。`PASS` 必须由审核结论产生，不能由 Worker 自行填写。

### Worker 启动时

1. 从 `AGENTS.md` 找到流程入口，只领取**一张** READY 任务卡。
2. 核验前置任务已合并，以及工作区所处 Git 基线。
3. 只读取任务卡、引用的 `spec` 章节、测试标准和必要接口/代码；不预加载全部文档。
4. 先确认目标、允许修改范围和验证命令；不清楚或冲突的事项先标记并上报，不擅自猜测关键决策。

### Worker 完成时

1. 执行任务相关自动化测试、类型检查/构建（以项目要求为准）。
2. 提交：修改文件、实现摘要、验证命令及结果、已知限制、是否偏离规格、基于哪个提交工作。
3. 转为 `REVIEW`，不自行标记 `PASS`。

### 每一轮审核

- **Lead**：检查范围、行为、相关测试、回归风险和代码可维护性；失败时只下发**可定位的阻塞项**。
- **Architect**：对照已批准的 intent/spec 检查设计一致性、公共接口和模块边界；普通任务轻量检查 diff 与 Lead 证据。
- 全部通过后方可合并/标记 `PASS`，更新 `progress.md`，将合并提交标识作为下一个任务的依赖基线。

### 会话重置原则

- **默认每个 Worker 任务开启新会话**，而非让一个 Worker 持续执行一个里程碑。
- Lead 可在一个里程碑内协调多个任务，但上下文显著膨胀、审核记录过长或准备进入新里程碑时，应基于文件和 Git **新开会话恢复**。
- Architect 不应长期背负所有 Worker 的聊天记录；每次任务复核优先使用独立、精简的审核上下文。
- 会话接续只从结构化交接记录恢复，不要求新 Agent 阅读完整前任聊天或无限压缩的会话摘要。

## 7. 审核标准与停止反复修复

### 7.1 问题分级

| 级别 | 示例 | 是否阻塞 |
|---|---|---|
| **BLOCKER** | 与批准规格冲突、数据错误、必要测试失败、安全漏洞、破坏接口兼容或越权修改 | 是 |
| **FOLLOW_UP** | 非必要重构、命名风格偏好、可延后优化、当前范围以外的改进建议 | 否；记录后续处理 |

每个 BLOCKER 反馈都要注明：**依据的文档条款或测试 → 发现的实际偏差 → 复现/定位证据 → 最小修复目标**。禁止仅凭“可以再优化”“不够优雅”等抽象评价反复否决。

### 7.2 失败升级

- 同一阻塞问题若**连续两轮修复仍未通过**，Lead 暂停继续派发原 Worker，先做根因分类：实现错误、测试/环境问题、任务拆分不合理、spec 不明确、上游业务决策冲突。
- 纯实现问题：重新定义最小修复范围，可用**新 Worker 会话**继续；保留失败证据。
- 设计不明确/契约冲突：交 Architect 修订 spec 或 plan，并重新走受影响 Gate。
- 需要改变目标/范围：交项目负责人批准 intent 变更，再更新下游文档。
- 不允许为了“通过测试”私自改测试预期、跳过测试、删除业务约束或无限累加兼容补丁。

### 7.3 变更控制

实现过程中发现合理的新需求，不直接纳入当前任务。记录为变更建议；仅当阻塞当前目标或被批准纳入时才修改相关基线。修改批准文档时记录**原因、影响、受影响任务、审核结果**，无需不加区分地重审全部项目。

## 8. 交接、Git 与故障恢复

**最小交接记录（每任务）**：

```yaml
id: M01-T03
status: REVIEW
base_commit: <启动基线>
work_commit: <工作分支提交或 diff 引用>
changed_files: ["...", "..."]
verification:
  - command: "<项目定义的测试命令>"
    result: PASS
spec_deviations: []
blockers: []
review:
  lead: PENDING
  architect: PENDING
```

- 只记录**客观结论**，不要复制长篇讨论、完整日志或隐藏推理。大日志存为可引用的 CI/日志文件。
- 以 Git 的代码版本和 `progress.md` 作为恢复锚点；发生上下文超限、Agent 中断或主机重启时，启动新会话、读取状态、核对 Git/测试后继续。
- 尽量一任务一独立提交或可识别的变更集；**审批前不合并主分支**，但可在隔离工作分支提交阶段性代码。
- 禁止将密钥、令牌、真实私密数据或生产配置复制到任务卡、Prompt、日志和 Git。

## 9. Definition of Done（完成定义）

**任务 PASS 条件**：范围内实现完成；必要测试/静态检查通过；可追踪到批准的 spec 和验收 Case；无 BLOCKER；Lead 和 Architect 审核通过；变更已按项目约定合并，`progress.md` 记录提交与结果。

**里程碑 APPROVED/COMPLETE 条件**：全部必需任务 PASS；该里程碑的集成与边界测试完成；对外接口和文档与实际代码一致；遗留非阻塞项已登记；下一里程碑能够依据文档及 Git 独立启动。

**项目交付条件**：在里程碑完成之外，另有系统级集成/端到端、部署/运行、安全及用户验收；对涉及概率输出（如 LLM 语义）的项目，应将**确定性代码测试**与**模型质量评测**分开，不以固定 Stub 通过等同于真实模型效果合格。

## 10. 项目特定扩展规则

通用规范只定义**方法**，不预先锁定编程语言、技术框架、目录命名、工具、部署方式或业务验收标准。

每个项目应建立一个简短的 `docs/project-development.md`，至少指明：

1. 本项目的业务/架构/数据/测试**权威文档及路径**。
2. 项目里程碑清单、任务 ID 规范、代码目录/所有权、依赖关系。
3. 运行时、语言、质量门禁命令、测试工具、分支/合并策略。
4. 安全、合规、生产发布、真实服务/模型测试等特殊 Gate。
5. 若需要覆盖通用规范的条款，**逐条写明覆盖项、原因、批准者和生效范围**；未覆盖条款沿用通用规范。

项目扩展只写**差异**和**引用**，不复制通用规范全文；通用规范升级不应无意重写项目已经冻结的业务设计。

## 11. 最小模板

以下模板只列关键字段；若项目已有权威文档，应引用既有内容，不为填写模板制造冗余。

### `intent.md`

```markdown
# <里程碑 ID> Intent
状态：DRAFT | REVIEW | APPROVED
基线：<Git commit / 版本>

## 问题与背景
## 目标与可观察结果
## 范围与非目标
## 成功标准
## 约束、依赖与未决决策
## 审核结论（负责人/日期/阻塞项）
```

### `spec.md`

```markdown
# <里程碑 ID> Spec
状态：DRAFT | REVIEW | APPROVED
依据：intent.md 的批准版本；项目架构基线

## 设计概览及边界
## 输入、输出、接口与数据契约
## 正常流程、边界与错误行为
## 不变量、兼容与安全要求
## 对应验收条件/测试引用
## 风险、权衡与未决项
## 审核结论
```

### `plan.md`

```markdown
# <里程碑 ID> Plan
状态：DRAFT | REVIEW | APPROVED
依据：spec.md 的批准版本

## 任务顺序与依赖
## 任务卡（逐项列 ID、spec 引用、文件边界、实现步骤、测试）
## 集成/回归步骤与 Gate
## 风险与回滚方式
## 审核结论
```

### `progress.md`

```markdown
# <里程碑 ID> Progress
基线：<批准的 plan 版本>

| 任务 ID | 状态 | 基线/提交 | 测试结果 | Lead | Architect | 阻塞说明 |
|---|---|---|---|---|---|---|
| M01-T01 | NOT_STARTED | - | NOT_RUN | - | - | - |

## 当前阻塞与待决策事项
## 下一可执行任务
```

## 12. 规范本身的维护

- 版本号：`vMAJOR.MINOR`。兼容性增强（模板/说明改进）增加 MINOR；影响门禁、角色或任务状态语义的变更增加 MAJOR。
- 本规范升级时，已进行中的里程碑原则上沿用启动时引用的版本；是否迁移由项目负责人明确确认。
- 建议只在实际开发中出现**可复现的流程问题**时升级规范，避免把规范本身变成持续优化、无法启动开发的工作项目。
