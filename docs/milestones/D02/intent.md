## 1. 问题与目标

D00、D01 已提供工程、HTTP 服务及数据库基础。后续内容路由、事件分析、知识分析和 Topic 匹配需要统一的模型调用基础：每次调用读取最新指令，明确区分指令与待分析数据，验证模型输出，并在失败时返回可处理的错误。

D02 提供这些公共能力以及不依赖真实模型的测试设施。模型业务判断、数据库写入和任务调度仍由后续里程碑负责。

## 3. Prompt 文件与目录对齐

当前六个文件位于 `config/prompt/`，设计约定为 `config/prompts/`。在 D02-T01 中按已确认设计对齐目录，保持文件内容不变，不同时保留两份可独立修改的副本。执行前后核对文件名与字节摘要，并明确独立 Worker 工作区如何获得这些尚未跟踪的文件。

| 功能 | 文件 | 是否读取 User Context |
|---|---|---|
| P-01 内容路由 | processing-route.md | 否 |
| P-02 Event 检索线索 | event-search.md | 否 |
| P-03 Event 归属与增量 | event-analysis.md | 否 |
| P-04 Knowledge 价值判断 | knowledge-analysis.md | 是，另读 user-context.md |

六份文件按技术设计进入 Git 版本管理；只处理明确列出的 Markdown，不批量提交整个 config 目录。纳入前检查是否含真实密钥或私密内容；若实际 User Context 含不应发布的私人资料，保留原文件并报告具体版本管理冲突，不自行公开、改写或以示例替换原文。公开版本与本地配置的安排须在受影响步骤执行前确定。

测试使用隔离临时文件和合成 User Context，不把实际私人背景复制进测试、日志或任务卡。格式化工具继续排除 Prompt 原文。

## 4. 成功标准

1. 五类调用按明确的文件映射读取指令；每次尝试都重新读盘。文件修改影响下一次调用，无需重启，不自动重分析历史内容。
2. Knowledge 调用读取两份文件后再发起一次模型请求；其他四类不读取或注入 User Context。文件缺失、不可读时明确失败，不用空文本或旧缓存继续请求。
3. 每种响应拒绝额外字段、错误类型、非法枚举和缺失必要字段。Event 动作分支分别验证：NEW_EVENT 不接受模型生成的 event_id；NEW_UPDATE/NO_INCREMENT 引用本次合法候选。Topic ID 只允许来自本次输入集合。
4. 正常空结果、valuable=false、无增量、不匹配按设计接受，不因没有业务产出而判为技术错误。别名、路由和 Topic ID 的去重及冲突校验遵循既有契约。
5. HTTP 请求由显式配置发起，密钥不进入日志或错误文本；超时和调用方取消能终止请求并清理资源。配置错误、网络错误、HTTP 错误和非法模型输出可以区分，具体分类与可重试边界在 Spec 中固定。
6. 调用与重试只设置一个明确的负责层，遵守既有“最多两次尝试”的规则，不能由 HTTP 客户端与上层各重试两次。用固定替身验证首次非法 JSON、重试前修改 Prompt、第二次重新读取的行为；不提前实现 Runtime 调度器。
7. 功能指令、User Context 和动态数据按各自用途组装；动态数据不成为可执行指令模板。固定测试证明请求结构和输入范围，真实模型能否抵抗指令注入仍由语义测试验证，不能由 Stub 测试宣称通过。
8. 五类功能各有少量固定合法/非法样例；HTTP 测试不依赖真实供应商、真实密钥或收费调用。现有 D00/D01 回归继续通过，干净检出能够安装、类型检查、测试、构建及运行既有 smoke。
9. 每卡经 Worker 自测、Lead 审核、Architect 复核后合并；集成验证及远程 CI 完成后再申请 D02 里程碑验收。PMT-11/12 等真实模型语义测试未执行时明确标 NOT_RUN，不冒称全部 PMT 用例通过。

## 5. 待确定事项与实施约束

- 沿用 Node 26.13.1 / npm 11.20.0、TypeScript strict、Zod 和原生 fetch，不因本阶段引入通用模型代理框架或多 Provider 编排平台。
- Provider 的请求/响应协议、配置字段、超时值、响应大小限制及错误映射在 G2 明确。优先从已有配置与项目设计核对；若缺少足以决定协议的信息，向负责人确认，不默认任意供应商都兼容同一接口。
- 真实供应商密钥、具体模型和付费语义测试不作为固定 P0 测试的前置条件；没有这些配置不阻塞 Prompt 读取、结构校验及 HTTP Mock 测试。
- 严格响应字段以技术契约和实际 Prompt 核对，不擅自改写 Prompt 来迎合代码。发现冲突时先定位并走受影响设计审核。
- 所有外部模型请求在数据库写事务之外。本阶段不引入数据库写入，也不改变 D01 表结构。
- 目录对齐、未跟踪文件进入独立工作区的方式、允许修改路径和测试命令在 Plan 中明确，不能通过 git add config 批量纳入无关文件。
- Intent 获负责人 G1 批准后制定 Spec；G2 通过后由新的 Paseo Lead 编写 Plan。沿用负责人要求，Plan 经 Architect 复核后交负责人审阅，明确批准后再委派 Worker。
- 当前只提交 Intent，不移动 Prompt、不启动正式开发。D01 心跳已停止，D02 不自动重建心跳。
