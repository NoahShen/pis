## 2. 目标与可观察结果

开发者从干净 checkout 出发，按开发说明即可安装依赖、检查类型、运行固定测试、构建并启动空服务；健康检查可用，进程能正常关闭。后续 Worker 能依赖统一命令和确定性测试设施执行独立任务。

## 3. 范围与非目标

范围严格对应现有四张任务卡，详细实现及文件边界留给 Spec 和 Lead 的 Plan：

| 既有任务 | 本阶段交付能力 |
|---|---|
| D00-T01 | TypeScript strict、Node.js LTS 版本约束、明确模块格式、依赖锁文件及可执行类型检查/构建 |
| D00-T02 | 测试运行器、Fixture、隔离的测试临时目录、可控 Clock 和 ID 接口；时间输出默认 `+08:00` |
| D00-T03 | Fastify 空服务、健康检查、Bearer 配置输入及基础 Pino 日志；启动/正常关闭 smoke |
| D00-T04 | 本地与 CI 统一验证脚本、代码格式及开发说明，记录已确认技术栈和尚待配置项 |

非目标：数据库表及 DAO、FTS5 实现、业务 API、六阶段队列和调度、内容采集和分析、LLM 调用、RSS 生成和云端发布。不提前安装或抽象当前任务不需要的完整业务组件。

## 4. 成功标准

1. 在明确记录的 Node.js LTS 环境下，可从干净 checkout 使用锁文件安装依赖，执行 `typecheck`、`test`、`build`；本地与 CI 使用一致的验证入口。
2. 固定测试能重复运行；Clock/ID 可控制，时间语义不依赖主机本地时区；测试临时数据相互隔离。
3. 编译产物可由 Node.js 启动，健康检查正常，服务能正常关闭，smoke 有可复现证据。
4. Bearer 配置与基础日志边界明确；日志不泄漏 Token 或完整敏感正文。
5. 开发说明能让新会话复现安装、检查、测试、构建、启动和关闭；明确当前能力与后续未决配置。
6. 四张任务均经 Worker 自测、Lead 审核、Architect 复核并合并，进度记录包含 Git 提交与验证证据；完成 D00 集成验收后才宣布里程碑完成。

D00 没有分配到既有 27 个历史冒烟 Case ID，不等于免测。具体工程验收条款与测试映射在 Spec/Plan 中明确，不冒用业务 Case 的 PASS，也不宣称全项目 P0 已通过。

## 5. 约束、依赖与未决决策

- 无前置开发里程碑；保持已确认的 TypeScript strict + Node.js LTS、Fastify、Pino 技术方向。
- Node.js 精确版本、ESM/CJS、测试运行器和验证命令细节在 G2/G3 及对应任务中落实；原生 SQLite 兼容性由 D01-T01 实测，FTS5 trigram 由 D01-T04 验证，不扩大 D00 范围。
- Git 已于 G1 审核前初始化，远程 `origin` 已配置，目前尚无提交基线。正式 Worker 开发前须建立可追溯 Git 提交基线，纳入文档和审核记录；不得把密钥或私密配置提交入库。
- 本地 Prompt 位于 `config/prompt/`，权威设计要求 `config/prompts/`。记录为资料路径待对齐项，最迟在 D02-T01 前解决；保持六份 Markdown 的单一来源，不改写其内容。该项不阻塞 D00 Intent 审核。
- LLM Provider、Source PATCH 策略、查询 Cursor、云端 RSS 平台等后续决策不阻塞 D00。
- G1 批准后才正式制定/审批 Spec；G2 通过后由 Paseo Lead 编写 Plan；G3 通过后才能派发正式 Worker 开发任务。
