## 1. 问题与背景

D00 已建立可安装、测试、构建及启停的工程。后续配置、采集、分析与发布模块需要可验证的 SQLite 存储基础；当前尚未验证 `better-sqlite3` 在既定 Node 工具链下的原生兼容性，也尚未把冻结 DDL、事务与派生 FTS 索引落实为运行代码。

D01 的目标是在真实临时 SQLite 数据库上证明既有存储设计可执行，为后续业务模块提供执行 SQL、提交事务和失败回滚所需的公共函数。沿用已批准的 11 张业务表及可重建 FTS5，不重新设计领域模型。

## 2. 目标与可观察结果

开发者从干净 checkout 安装依赖后，能够在隔离的临时数据库上初始化冻结结构、执行数据库查询和写入、将需要一起提交的操作放在同一事务中、验证约束与回滚，并按单个 Event 刷新或从业务事实全量重建检索索引。连接关闭及测试清理可重复执行，不依赖现存数据库、外部服务或真实 LLM。

## 3. 范围与非目标

仅落实现有四张任务卡；具体模块接口、文件边界、依赖精确版本及执行次序在 G2/G3 明确。

| 既有任务 | 本阶段交付能力 | 验收映射 |
|---|---|---|
| D01-T01 | 集成 better-sqlite3；连接设置 WAL、每连接外键及 5000ms busy timeout；隔离临时 DB 与关闭清理；验证原生安装/加载 | DB-01 的运行时能力部分、DB-02；完整 DDL 验证随 T02 集成 |
| D01-T02 | 以冻结 DDL 为唯一权威源建立初始化路径；验证 7 核心表 + 4 辅助表、索引、唯一/外键/枚举/布尔/JSON 约束 | DB-01、DB-03～DB-08 的数据库层、DB-15 |
| D01-T03 | 封装执行 SQL、提交事务和失败回滚所需的公共函数，区分 SQLite 错误类型；复用 D00 的时钟、ID 生成和时间格式工具 | DB-09、DB-10、DB-12 的基础能力 |
| D01-T04 | Event FTS5 trigram 建立、单 Event 刷新、全量重建；验证全历史文本、中文词及别名检索基础 | DB-11、DB-14 初始版 |

这里的数据库操作采用 better-sqlite3 的同步调用：一条操作执行结束后，函数直接返回结果或抛出错误，再执行下一步，不返回 Promise。公共函数只覆盖当前任务需要的重复操作；业务代码仍直接编写 SQL。

非目标：业务管理/历史查询 API、通用 ORM、历史数据库迁移系统、六阶段业务实现、Runtime 队列及重试调度、LLM/Prompt、Event 归属和增量语义、完整候选排序、RSS 和生产部署。不新增业务表、Outbox、持久化任务或失败状态表，不改 Prompt 内容及目录。

## 4. 成功标准

1. 既有 Node `26.13.1` / npm `11.20.0` 下，可从锁文件安装并加载明确版本的 better-sqlite3；记录驱动与实际 SQLite 版本、平台和原生安装结果。至少完成本地 darwin-arm64 与既有 Linux CI 的实测；未测平台明确标 NOT_RUN。
2. 真实临时文件数据库能执行完整冻结 DDL，无擅自增删表/字段或放宽约束；FTS5 trigram 与 JSON 函数可用。多个实际连接均满足 `foreign_keys=ON`、`busy_timeout=5000`，数据库处于 WAL 模式。
3. 用真实 SQL 验证唯一约束、普通外键、联合主键、枚举/布尔 CHECK、JSON 数组检查和 Source Item 非 NULL Content 引用唯一性；失败写入不覆盖既有记录。明确 SQLite 不负责多态目标的业务存在性校验。
4. 同一事务内的多条写入全部成功后一起提交，任一步失败则全部撤销；事务内只做必要的数据库操作，不等待 HTTP 请求或 LLM 调用。能识别数据库被其他连接占用导致的锁冲突；测试须在限定时间内结束，并关闭连接、清理临时文件。Runtime 的有限重试留到对应里程碑。
5. 时间值复用既有确定性接口，统一为 ISO 8601 TEXT、显式 `+08:00`；不依赖机器时区或 SQLite CURRENT_TIMESTAMP 生成业务时间。
6. 每个 Event 在 FTS 中逻辑上恰好一行；文本包含冻结设计要求的 Event 字段、确认别名与全部历史 Update。单条刷新与全量重建一致，能随业务数据在同一短事务中回滚，不破坏其他 Event 或原始业务事实。
7. trigram 检索与普通 Entity/Alias 索引的短词基础分别验证，不假设 trigram MATCH 能有效命中 1～2 字符；完整候选召回与上下文组装留给 D08。
8. 沿用 `npm run verify` 完成类型检查、固定测试、构建、服务 smoke 和格式验证，保留 D00 回归；从干净 checkout 验证安装及统一入口，并记录远程 CI 结果。
9. 四张任务均按 Worker 自测 → Lead 审核 → Architect 复核逐项通过后合并；D01 集成验收通过后才宣布里程碑完成。

测试覆盖按阶段如实记录：DB-03/06/07 的业务输入校验、DB-09 的六阶段故障注入、DB-10 的各业务时间语义、DB-12 的 Runtime 重试、DB-13 的业务服务拒绝悬空多态目标等，仍由后续对应模块完成。D01 仅验证相关数据库事实和基础能力，不将部分覆盖标为整项业务用例 PASS。

## 5. 约束、依赖与未决事项

- D00 已完成并通过远程 CI；本阶段继续采用 TypeScript strict、NodeNext ESM、better-sqlite3 + 直接 SQL、无 ORM。
- better-sqlite3 及必要类型依赖的精确版本、预编译包或本地构建需求，由 Spec/Plan 明确并在 T01 实测；不为安装方便擅自切换驱动或 Node 基线。需要工具链变更时，提供证据并重走受影响门禁。
- 冻结 DDL 面向新建数据库；不能把重复 CREATE IF NOT EXISTS 当作历史库迁移。落地 SQL 与权威文档之间的校验方式在 Spec/Plan 明确，避免维护分叉版本。
- FTS5 trigram 或冻结 DDL 在目标驱动不成立时，标 BLOCKED，提交版本、SQL 和复现证据给 Architect；不得偷换为 LIKE/向量检索或擅自改表。设计明确允许的短词索引检索不属于替换 trigram。
- 本阶段只用隔离测试数据库，不触碰已有私密配置或实际业务数据；原有未跟踪 `config/` 不提交。
- Prompt 路径差异仍最迟 D02-T01 前对齐，不阻塞 D01；LLM Provider、RSS 云端平台等未决项不进入本阶段。
- 本 Intent 获 G1 批准后才正式制定 Spec；G2 通过后由新的 Paseo Lead 会话编写 Plan；G3 通过后逐任务委派新的 Paseo Worker。当前不派发开发任务，不恢复心跳。
